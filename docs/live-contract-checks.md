# Live contract checks (v0.4.0)

Checked on 2026-09-17 against a real account in Chrome on macOS.

**Scope.** These checks cover the API contract only: each request was sent from a page on the site, built the same way the content script builds it. The extension path (side panel, orchestrator, message router) was not part of this run. It stays untested on a live account until `dist/` is loaded in Chrome and a migration is run through the side panel. The stubbed Playwright scripts in `scripts/` cover that path against fake sites.

Test items were left in place for manual removal:
- Claude project `PortSmith test (delete me)`
- Gemini Gem `PortSmith test Gem (delete me)`

IDs, org IDs and account details are left out on purpose.

## Claude writes

Source of the request shapes: `src/content-scripts/claude/importer.ts` and `claudeRequest` in `src/content-scripts/claude/api.ts`. JSON bodies were sent with `Content-Type: application/json`. The upload used `FormData` with the field `file` and no manual `Content-Type`, so the browser set the multipart boundary. The org ID came from the `lastActiveOrg` cookie, which `document.cookie` can read.

All paths below are relative to `/api/organizations/{org}`.

| # | Request | Body | Status | Response keys |
|---|---------|------|--------|---------------|
| 1 | `GET /projects?limit=100&offset=0` | none | 200 | array; items: `archived_at, archiver, created_at, creator, description, docs_count, files_count, is_harmony_project, is_private, is_starred, is_starter_project, moved_to, name, permissions, settings, subtype, type, updated_at, uuid` |
| 2 | `POST /projects` | `{name, description, is_private: true}` | 201 | same as a list item, including `uuid` |
| 3 | `PUT /projects/{id}` | `{prompt_template}` | 202 | project detail (list keys plus `has_folder, organization_role, prompt_template`) |
| 4 | `POST /projects/{id}/docs` (`notes.md`) | `{file_name, content}` | 201 | `content, content_length, created_at, estimated_token_count, file_name, project_uuid, uuid` |
| 5 | `POST /projects/{id}/upload` (PDF, multipart `file`) | FormData | 200 | `created_at, document_asset, file_kind, file_name, file_uuid, path, preview_asset, sanitized_name, size_bytes, success, thumbnail_asset, user_uuid, uuid` |
| 6 | `POST /projects/{id}/docs` (`project-memory-from-chatgpt.md`) | `{file_name, content}` | 201 | same as #4 |
| 7 | `GET /projects/{id}` | none | 200 | detail keys (as #3, plus `cowork_bound_device`) |
| 8 | `GET /projects?limit=100&offset=0` (after create) | none | 200 | array; contains the new project's `uuid` |

Observations:
- The list items still have no `prompt_template`, so reading `/projects/{id}` for instructions (as the extractor does) is still required.
- The success codes are 201 and 202, not only 200. `claudeRequest` accepts any `ok` status, so this is fine.
- The create response has `uuid` as a UUID string, so `isUuid` passes.
- The upload response has both `file_uuid` and `uuid`. The importer reads `file_uuid` first.
- After the run, the detail showed the exact name, the exact `prompt_template`, `is_private: true`, `docs_count: 2` and `files_count: 1`. `GET /projects/{id}/docs` listed `notes.md` and `project-memory-from-chatgpt.md`.
- The project page showed the instructions, `notes.md`, the PDF and `project-memory-from-chatgpt.md` under Context. The Memory panel stays empty ("Project memory will show here after a few chats"), which is expected because memory travels as a document.

Mismatches: none.

Duplicate check: the list returned the new project by name (#8), which is the data `CLAUDE_FIND_PROJECTS` uses. The side panel question ("A project named ... is already in Claude. Create another one?") still needs a run through the extension. The stubbed E2E script `scripts/e2e-claude-autofill.mjs` covers it.

## Gemini create and Gem list

Source of the request shapes: `src/content-scripts/gemini/batchexecute.ts`, `session.ts`, `extractor.ts` and `importer.ts`. The create `f.req` was generated by running `buildCreatePayload` from `importer.ts` (compiled with esbuild) and wrapped as `encodeRequest` does. It was not written by hand.

### Session

`GET https://gemini.google.com/app` returned 200 with `SNlM0e`, `cfb2h` and `FdrFJe` present, and `TuX5cc` for the language.

### Create (`oMH3Zd`)

- `POST /_/BardChatUi/data/batchexecute`
- Query: `rpcids=oMH3Zd, hl, _reqid, rt=c, source-path=/app, bl, f.sid`
- Headers: `Content-Type: application/x-www-form-urlencoded;charset=utf-8`, `X-Same-Domain: 1`, `x-goog-ext-525001261-jspb`, `x-goog-ext-73010989-jspb`
- Body: `at=<SNlM0e>&f.req=<below>`

```
[[["oMH3Zd","[[\"PortSmith test Gem (delete me)\",\"Live contract check for PortSmith 0.4.0. Safe to delete.\",\"You are a test Gem for PortSmith. Answer briefly.\",null,null,null,null,null,0,null,1,null,null,null,[]]]",null,"generic"]]]
```

Response: HTTP 200, with a `)]}'` prefix and these frames: `wrb.fr` (ours), `di`, `af.httprm`, `e`.
- Our frame: `["wrb.fr", "oMH3Zd", "<json>", null, null, null, "generic"]`
- The parsed body is `[gemId (string, 12 chars), boolean]`. `createGem` reads `body[0]`, so it gets the ID.

The Gem editor (`/gems/edit/{id}`) showed:
- the exact name, description and instructions;
- "Default tool": "No default tool";
- "Knowledge": empty.

The 15-element payload is accepted without those newer fields, which fall back to their defaults.

### List (`CNgdBe`)

- Payload: `[2,["en"],0]`, with identifier `custom`.
- Response: HTTP 200. The `wrb.fr` frame is tagged `custom`. The parsed body has 3 entries, and the Gem list is at index 2, as `extractor.ts` expects.
- Before the create: 2 custom Gems, none named like the test Gem.
- After the create: 3 Gems. The test Gem was found by name with the same ID the create returned.
- Each entry is `[id, [name, description], [instructions], ...]`, and the name, description and instructions matched exactly.

This means the duplicate check has the data it needs. The side panel warning itself still needs a run through the extension.

### Multi-account (`/u/N/`)

A second Google account was signed in and served at `/u/1/app`.

| Request | Result |
|---------|--------|
| `GET /app` and `GET /u/1/app` | Both 200, with different accounts and different `SNlM0e` values |
| Account 0 tokens on `/_/BardChatUi/data/batchexecute` | 200, lists account 0's Gems (the test Gem is here) |
| Account 1 tokens on `/u/1/_/BardChatUi/data/batchexecute` with `source-path=/u/1/app` | 200, lists account 1's Gems (0, no test Gem) |
| Account 1 tokens on the unprefixed URL | 400 with an `er` frame |
| Account 0 tokens on the `/u/1/` URL | 400 with an `er` frame |

Conclusions:
- Tokens are per account, and the URL prefix must match the account the tokens came from.
- PortSmith always fetches `https://gemini.google.com/app` (`session.ts` and `extractor.ts`) and always posts to the unprefixed batchexecute URL. The requests are consistent, so they succeed, but they always act on account 0 (`/u/0`).
- If the user is working in a `/u/1/` tab, Gems are read from and created in the default account, not the one on screen. Nothing reports an error.
- The orchestrator also opens `https://gemini.google.com/app` when no tab exists, and it matches any Gemini tab.

Proposed fix (not applied, since no payload was rejected):
1. In `session.ts`, take the account prefix from the tab that runs the content script: `const prefix = /^\/u\/\d+/.exec(location.pathname)?.[0] ?? ""`.
2. Fetch `${origin}${prefix}/app` for the tokens and keep `prefix` in `GeminiSession`.
3. In `batchexecute.ts`, post to `${origin}${prefix}/_/BardChatUi/data/batchexecute` with `source-path=${prefix}/app`.
4. Have `extractor.ts` use the shared `session.ts` instead of its own copy, so both paths agree.
5. In the side panel, show which account is in use (for example "Gemini account 2 (/u/1/)") before a migration starts, and use the same tab for extraction and import.
